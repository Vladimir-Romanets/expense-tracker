# Senior Frontend Developer (Next.js + React + RHF)

This skill sets senior-level standards for working with the Next.js App Router, React, and react-hook-form. The goal is code that wouldn't need to be rewritten in code review: type-safe, performant, with a clear architecture.

**Section priority**: "Forms: react-hook-form + zod" and "Components and structure" are the primary focus of this skill — apply their rules as strictly and thoroughly as possible. "Code review and refactoring" and the architecture section are supporting material — apply as situations call for it, but don't treat them as the main agenda.

## How to operate

1. Understand the context first: check package.json (React/Next versions), tsconfig, the existing folder structure and naming conventions — don't impose your own style over an existing project's.
2. Before writing code, briefly (1-2 sentences) state which approach you're choosing and why, if there's a fork in the road (e.g. Server Action vs API route, controlled vs uncontrolled).
3. Write production-ready code right away: with types, error handling, and edge cases — not "finish it yourself" scaffolding.

## Default stack and versions

- Next.js 15+ (App Router, Server Components by default, `"use client"` only when actually needed: hooks, browser APIs, interactivity)
- React 19 (Actions, `useActionState`, `useOptimistic` where appropriate — don't force them in artificially)
- TypeScript strict mode
- react-hook-form v7 + zod (via `@hookform/resolvers/zod`)
- **Tailwind CSS v4** for styling, unless the project specifies otherwise (see the dedicated section below for v4-specific conventions)

If the project uses different versions, adapt to those instead of this list.

## Tailwind CSS v4 conventions

Tailwind v4 changed its configuration and setup model — don't default to v3 patterns.

- **CSS-first config**: no `tailwind.config.js` by default. Theme customization (colors, fonts, spacing, breakpoints) goes in CSS via the `@theme` directive, in the main stylesheet:
  ```css
  @import "tailwindcss";

  @theme {
    --color-brand-500: oklch(0.64 0.2 25);
    --font-display: "Inter", sans-serif;
    --breakpoint-3xl: 120rem;
  }
  ```
- Entry point is `@import "tailwindcss";` — not the old `@tailwind base; @tailwind components; @tailwind utilities;` directives.
- No PostCSS config boilerplate needed for the common case — v4 auto-detects content sources; don't add a `content: []` array unless the project genuinely needs to override detection (e.g. content outside the project root).
- Only add a `tailwind.config.js`/`.ts` file if the project already has one or genuinely needs JS-level config (plugins that require JS, complex programmatic theme generation) — otherwise stick to CSS-first.
- Arbitrary values and container queries work natively (`@container`, `@sm:`, etc.) without a plugin — use them instead of manual media query hacks when a component needs container-based responsiveness.
- Use CSS variables generated by `@theme` (e.g. `var(--color-brand-500)`) when you need the raw value outside of a utility class (inline styles, JS-driven values like chart colors) — don't hardcode hex/oklch values that duplicate the theme.
- Check the project's actual Tailwind version in package.json before assuming v4 — if it's still on v3, follow v3 conventions (`tailwind.config.js`, `@tailwind` directives) instead.

## Forms: react-hook-form + zod (reference pattern)

Always: validation schema in zod → `zodResolver` → types via `z.infer`. Don't duplicate types manually if a zod schema already exists.

```tsx
"use client";

import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";

const schema = z.object({
  email: z.string().email("Invalid email"),
  amount: z.coerce.number().positive("Amount must be greater than zero"),
});

type FormValues = z.infer<typeof schema>;

export function ExpenseForm({ onSubmit }: { onSubmit: (values: FormValues) => Promise<void> }) {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm<FormValues>({
    resolver: zodResolver(schema),
    defaultValues: { email: "", amount: 0 },
  });

  return (
    <form onSubmit={handleSubmit(onSubmit)} noValidate>
      <input {...register("email")} aria-invalid={!!errors.email} />
      {errors.email && <p role="alert">{errors.email.message}</p>}

      <input type="number" step="0.01" {...register("amount")} aria-invalid={!!errors.amount} />
      {errors.amount && <p role="alert">{errors.amount.message}</p>}

      <button type="submit" disabled={isSubmitting}>
        {isSubmitting ? "Saving…" : "Save"}
      </button>
    </form>
  );
}
```

Rules to follow at all times:
- `defaultValues` is mandatory — without it RHF warns about controlled/uncontrolled inputs and causes flickering re-renders.
- Complex/nested fields (arrays, dynamic rows) — via `useFieldArray`, not a manual `useState` array.
- Selects, checkboxes, custom UI components (not native `<input>`) — via `Controller`, not manual state syncing.
- Server errors (409, 422 from the API) — via `setError("root", { message })` or `setError("fieldName", ...)`, never a separate `useState<string | null>` for form errors.
- Async uniqueness validation (email already taken, etc.) — on blur, not on every keystroke; debounce on the resolver side, not the UI.
- In the App Router, a form can submit directly to a Server Action — if the project already does this, use `useActionState` instead of a manual `onSubmit` + fetch. Don't reinvent — check what pattern is already established in the repo first.

### Dynamic field arrays (useFieldArray)

Example: expense/receipt line items where the user adds an arbitrary number of entries.

```tsx
const schema = z.object({
  items: z.array(
    z.object({
      name: z.string().min(1, "Required field"),
      price: z.coerce.number().positive(),
    })
  ).min(1, "Add at least one item"),
});

const { control, register } = useForm<z.infer<typeof schema>>({
  resolver: zodResolver(schema),
  defaultValues: { items: [{ name: "", price: 0 }] },
});

const { fields, append, remove } = useFieldArray({ control, name: "items" });
```
Use `field.id` from `fields`, not `index`, as the React `key` — otherwise removing an item from the middle of the list breaks input focus/state.

### Custom UI components (not a native input) via Controller

For selects/date-pickers/checkbox groups from a UI kit (or handwritten) — don't wire them manually via `watch`/`setValue`, use `Controller`:

```tsx
<Controller
  control={control}
  name="category"
  render={({ field }) => (
    <Select value={field.value} onValueChange={field.onChange}>
      {/* options */}
    </Select>
  )}
/>
```

### Files (e.g. receipt/image upload)

Files aren't validated with a plain zod `.string()` — register as `FileList`/`File[]` and check size/mime separately:

```tsx
const schema = z.object({
  receipt: z
    .instanceof(File)
    .refine((f) => f.size <= 5 * 1024 * 1024, "File larger than 5MB")
    .refine((f) => ["image/png", "image/jpeg"].includes(f.type), "PNG/JPEG only"),
});
```
A file input is always `uncontrolled` by value (`{...register("receipt")}` with no `value`) — the browser doesn't let React control `input[type=file]`.

### Multi-step forms

One `useForm` for the whole flow (not a separate form per step) — this way data isn't lost between steps and validation of the entire form works on final submit. Partial validation of the current step — via `trigger(["fieldA", "fieldB"])` before advancing to the next step.

## Components and structure

- Server Component by default. `"use client"` only on leaf interactive components (a form, a button with a handler, anything using hooks) — don't hoist the directive higher up the tree than necessary.
- Composition over prop drilling: if a prop is passed through 3+ levels without being used, that's a signal to extract it into context or restructure the tree, not to keep threading it through.
- One component = one responsibility. If a component file grows past ~150-200 lines, split it (subcomponents, hooks, helpers).
- Custom hooks for reusable logic (`useDebounce`, `useMediaQuery`, domain hooks like `useExpenseFilters`) — don't copy-paste logic between components.
- Naming: `PascalCase` for components/component files, `camelCase` for hooks and utilities, `kebab-case` for non-component files, unless the project already has a different convention.

### Generating typical components — defaults to bake in

When generating new components (even if not explicitly requested), bake in:
- **Table/data list**: empty state, loading state (skeleton, not a spinner over the whole block), pagination or infinite scroll — ask which if it's not obvious from context; sorting — via query params/URL state if it's a Next.js page (preserves state on share/reload).
- **Card**: an explicit prop interface (`interface XProps`), not `any`/`Record<string, unknown>`; if the card is clickable, wrap it in `<Link>`, don't attach `onClick` with `router.push` to a `div`.
- **Layout/page**: split into `page.tsx` (Server Component, data) and separate files for interactive client pieces — don't push an entire page into `"use client"` for the sake of one button.
- **Modal/dialog**: manage open state via URL state (`?modal=edit-expense`) if the modal should survive reload/share, otherwise local `useState` in the nearest common parent.
- Always generate components with accessibility in mind by default: semantic tags, `aria-*` for non-native interactive elements, `alt` for images — don't wait for a separate a11y request.

## API layer typing

- Never `any` for an API response. If the backend is TypeScript (as in the Express/Drizzle setup), share types through a common monorepo package where possible, or generate/duplicate a strictly typed contract.
- Data shapes coming from the backend → a separate zod schema for runtime response validation when the data is critical (not for every GET, but definitely for form submit responses and financial/payment data).
- Wrap fetch in a typed client helper, don't scatter bare `fetch()` calls across components.

## Performance and Core Web Vitals

Keep in mind for any nontrivial UI:
- LCP: `next/image` with explicit `width`/`height` or `fill` + `sizes`, `priority` loading only for hero content.
- CLS: reserve space for async content (skeleton with fixed dimensions), don't let layout jump after hydration.
- INP: debounce/throttle heavy handlers, `useMemo` for heavy computations — but don't memoize everything preemptively without profiling.
- Split heavy client bundles via `next/dynamic` where a component isn't needed on first render (modals, charts, editors).

## Code review and refactoring

When fixing existing/legacy code rather than writing from scratch:
1. State what you're changing and why (1-2 bullet points) before producing the full diff.
2. Change the minimum necessary — don't restyle the whole file in passing unless asked.
3. Explicitly flag any bug or antipattern outside the current task's scope — but don't fix it without being asked, just point it out.
4. Check for unnecessary re-renders from unstable references (inline objects/functions in props without `useCallback`/`useMemo` where it actually matters — don't cache everything preemptively).

## When in doubt

If it's unclear which pattern to choose (Server Action vs API route, Context vs prop, Zustand/Redux vs local state) — first check what's already used in the project and follow that. If the project is new and there's no established pattern yet, choose one yourself and briefly explain the choice — don't ask about every minor decision separately.
